# Аналитика «Граф денег»

Один локальный запуск читает три Parquet из `docs/data/` и создаёт выгрузки в `analysis/out/`: роли и приоритеты 2 248 клиентов, кластеры, топ проверки и три дополнительных отчёта. Основной сигнал приоритета — модельная атрибуция переводов источникам seed. Все выводы — гипотезы для проверки, не утверждения о виновности, фактическом остатке денег или управлении счетами.

## Запуск

Из корня репозитория:

```bash
python3 -m venv analysis/.venv
analysis/.venv/bin/python -m pip install -r analysis/requirements.txt
analysis/.venv/bin/python analysis/run.py
```

После установки зависимостей полный пересчёт — одна команда:

```bash
analysis/.venv/bin/python analysis/run.py
```

Зависимости: pandas `>=2.2,<3`, NumPy `>=1.26,<3`, PyArrow `>=15`, NetworkX `3.2.1`. Контрольный запуск: Python 3.9.6, pandas 2.3.3, NumPy 2.0.2, PyArrow 21.0.0, macOS arm64. Диапазоны позволяют устанавливать подходящие сборки на Python 3.9–3.13, но побайтовая воспроизводимость гарантируется проверкой только в использованном окружении. После обновления библиотек нужно повторить тесты.

Параметры: `--data PATH`, `--out PATH`, `--top 30` (минимум 20). Пути по умолчанию привязаны к расположению скрипта, переданные относительные пути — к текущей директории. `docs/` используется только для чтения. Расчёт не требует сети, LLM или внешних данных. Контракт входа: июль 2026, переводы от 5 000 KZT, глубина 4. Для другого периода измените `PERIOD_START`, `PERIOD_END`, `EARLY_END`.

Тесты и внешний замер полного процесса:

```bash
analysis/.venv/bin/python -m unittest discover -s analysis/tests -v
/usr/bin/time -p analysis/.venv/bin/python analysis/run.py
```

## Направленные признаки

Сначала в граф добавляются все `gid` из `nodes.parquet`, в том числе 19 изолированных seed, затем рёбра. Суммы и количество транзакций сверяются с `transactions.parquet` отдельно для каждой пары; допустимое расхождение суммы — 0.01 KZT. Проверяются схемы, типы, пропуски, уникальность узлов и рёбер, известность концов рёбер, глубина, даты и порог сумм.

Обозначения: `I/O` — наблюдаемые вход/выход в KZT; `di/do` — число разных плательщиков/получателей; `ti/to` — количество входящих/исходящих переводов. Направление сохраняется во всех этих признаках.

- `r = pass_through = O/I` определено только для не-seed при depth<4 и I>0; иначе пусто. Это отношение видимых переводов, не полный баланс.
- `m = fast_share` — доля входа, которую можно FIFO-сопоставить с выходом в тот же день или через 1–2 дня. Один KZT не используется дважды. Это совместимость сумм и дат, не установление происхождения денег; внутри дня реальный порядок неизвестен.
- `e = early_in_share` — доля входа до 24.07 включительно. Если e мала, последующий выход мог не попасть в июльское окно. При нулевом входе m=e=0.
- `max_payers_day` и `sync_days` — максимум разных плательщиков за день и число дней с 3+ плательщиками.
- `split_days` — число сочетаний «получатель–день», в которых отправитель сделал 3+ перевода. Несколько получателей в один день считаются отдельно. Это не доказательство намеренного дробления.
- `return_flows` — число направленных циклов длины 2–3 в месячном графе, без проверки последовательности дат.
- `stable_routes` — число пар (A,C), для которых есть хотя бы два выхода B→C, каждому из которых предшествует вход A→B за 0–2 дня. Один вход может поддерживать оба выхода; это кандидат на маршрут, не доказательство двух независимых полных цепочек.

## Деньги seed: модель смешивания и даты

Модель маркирует суммы источниками seed и пропорционально переносит метки при смешивании (haircut). «Неатрибутированные деньги» означают отсутствие известной метки; они не считаются доказанно законными или не связанными с делом.

Для каждого дня:

1. Строится направленный граф переводов дня и его **сильносвязные компоненты**. Между компонентами получается ациклический граф.
2. Компоненты обрабатываются в топологическом порядке. Входы из уже обработанных компонент доступны в тот же день. Это допущение о возможной последовательности операций, а не восстановленные часы переводов.
3. **Внутри компоненты все расходы рассчитываются до её внутренних приходов.** Встречные переводы, включая самоперевод, не финансируют себя. Внутренние поступления становятся доступны для расходов со следующего дня. Такой выбор симметричен относительно клиентов и не зависит от порядка строк или числовой величины gid.
4. Пусть P — модельная сумма на начало обработки узла, Lₛ — её часть с меткой s, O — весь выход дня. Знаменатель F=max(P,O). Каждый перевод на a KZT переносит по каждой уже известной метке `a × Lₛ/F`. Недостающая ликвидность `F−P` у обычного клиента считается неатрибутированной.
5. У seed **вся ещё не маркированная часть его выхода** получает собственную метку. Это касается и ранее наблюдавшегося неатрибутированного входа, а не только недостатка ликвидности. `seed_origin_kzt` — впервые маркированная при выходе сумма; название не означает доказанное происхождение или принадлежность денег.
6. После списаний зачисляются переводы. Уже известные метки никогда не меняются при прохождении через другой seed.

Такой расчёт конечен и не требует итерационной сходимости. Цикл `seed A↔seed B` с переводами по 100 тыс. в один день предполагает 200 тыс. начальной ликвидности, маркирует по 100 тыс. у каждого источника и сохраняет 200 тыс. в модели. Это консервативное допущение о доступности поступлений, а не утверждение, что у клиентов действительно были такие остатки. На данных внутренние однодневные циклы затрагивают **124 узла**, сумма их внутренних приходов — **14 683 319.97 KZT** (`same_day_cycle_in_kzt`).

### Собственные возвраты и физический учёт

Модель сохраняет все метки для проверки балансов. Для роли и приоритета seed **его собственная метка исключается**, даже если деньги вернулись через нескольких посредников:

```text
seed_in_total_kzt = все наблюдаемые поступления с любыми метками seed
seed_self_return_kzt = поступления с собственной меткой получателя-seed; 0 у остальных
seed_in_kzt = seed_in_total_kzt − seed_self_return_kzt
seed_sources = число учитываемых источников с вкладом ≥5 000 KZT; собственный исключён
seed_forwarded_kzt = выход с учитываемыми метками; у seed только чужие метки
seed_forwarded_share = seed_forwarded_kzt / seed_in_kzt; 0 при нулевом входе
seed_kept_kzt = seed_in_total_kzt − seed_out_kzt + seed_origin_kzt
```

`seed_out_kzt` и `seed_kept_kzt` продолжают учитывать **все** метки: исключать собственные возвраты из физического баланса нельзя. Проверяются дневные остатки, баланс каждого узла, границы каждого потока и общий инвариант `sum(seed_origin_kzt)=sum(seed_kept_kzt)`. Суммирование поступлений по узлам может повторно учитывать одни и те же деньги на разных шагах или при возврате; это оборот, а не уникальный объём средств.

Узлы с большим общим оборотом и малой модельной долей seed могут получать меньший приоритет. Это осознанный выбор очереди проверки по данному делу; он не исключает значимость таких узлов для других проверок.

## Правила ролей

Правила проверяются **сверху вниз**. Первое выполненное — основная роль; следующее — `secondary_role`. `role_score` — эвристическая сила признаков основной роли, не вероятность и не accuracy: разметки для калибровки нет. `c(x)=min(max(x,0),1)`, `k=seed_sources`, `[условие]` равно 1 или 0.

| № | Роль | Минимальное условие | role_score |
|---|---|---|---|
| 1 | coordinator | depth<4; di≥2, do≥3, k≥2 | `0.55+0.15c((k−2)/3)+0.10c(di/10)+0.10c(do/20)` |
| 2 | consolidator | di≥3, do≤di/2 | `0.35+0.20c((di−3)/7)+0.10c(ti/20)+0.10[max_payers_day≥3]+0.15c((k−1)/2)` |
| 3 | distributor | depth<4; do≥5 | `0.30+0.25c((do−5)/45)+0.10c(to/50)+0.10[O≥1 млн]` |
| 4 | transit | не seed, depth<4, I>0, 0.8≤r≤1.2 | `0.35+0.25m+0.10c(1−abs(r−1)/0.2)+0.10[ti≥2 и to≥2]+0.10[min(I,O)≥100 тыс.]` |
| 5 | terminal | не seed, depth<4, I>0, r≤0.1 и (I≥100 тыс. или ti≥3) | `0.30+0.20c((ti−1)/4)+0.15e+0.10[I≥100 тыс.]` |
| 5 | terminal при depth=4 | p≥0.75, похожих узлов≥100 | `0.20+0.15c((p−0.75)/0.25)` |
| 6 | peripheral | ни одно правило не выполнено | 0.50 — обычный узел; 0.30 — seed; 0.20 — depth=4; 0.10 — нет рёбер |

У изолята все специальные правила выключены. На глубине 4 возможны только consolidator, terminal по аналогам или peripheral; поддержка ограничена **0.35**. Нулевой наблюдаемый выход границы не используется как доказательство удержания денег. При consolidator на границе виден только сбор по входам, а реальное число получателей неизвестно. У seed не бывает transit или terminal. Score округляется до 6 знаков.

Порядок отражает приоритет структурных признаков: совместный сбор и распределение денег нескольких seed; затем воронка сбора; затем веер; далее сопоставимые суммы транзита и малый видимый выход. Например, «5 плательщиков → 1 получатель, всё передал» получает consolidator и вторичную transit. Слабый признак не всегда отбрасывается: один вход и выход по 20 тыс. дают transit с низким score. Peripheral означает отсутствие выполненного правила, а не доказанную незначимость клиента.

Пороги экспертные: 3 плательщика — несколько источников, 5 получателей — минимальный веер, ±20% — сопоставимость сумм, r≤0.1 — малый **видимый** выход, 100 тыс. — существенная сумма. Они не устанавливают фактический остаток. Поздний вход снижает поддержку terminal, но не запрещает эту гипотезу. Поддержка структурных ролей seed основана на наблюдаемых положительных признаках, а не на отношении O/I.

`patterns`: seed; isolated; boundary; external_funding (external_share≥0.5 при O≥100 тыс.); fast_transit (m≥0.5); sync_inflow; split; return_flow; stable_route; late_inflow (depth<4, I>0, e<0.8). Это поводы для проверки, не признаки виновности.

## Приоритет

```text
M = c(log10(max(seed_in_kzt, 5000) / 5000) / 3)
K = c((seed_sources − 1) / 3)
R = W(role) × role_score
priority_score = round(0.50M + 0.20K + 0.30R, 9)
```

M насыщается при 5 млн KZT; 5 тыс. дают 0, 50 тыс. — 1/3, 500 тыс. — 2/3. K насыщается при четырёх источниках. W: coordinator=1.0, consolidator=0.9, transit=0.7, terminal=0.7, distributor=0.6, peripheral=0. Общий оборот не входит напрямую, но учитывается частью ролевых признаков. Статус seed бонуса не даёт; его собственные возвраты не входят в M и K. Сортировка: сохранённый priority_score↓, при равенстве gid↑.

`why` содержит признаки, вторичную роль и разложение приоритета. Текстовые числа округлены для чтения, точный пересчёт делают по числовым колонкам money_score, sources_score, role_part с погрешностью до 2×10⁻⁹.

## Кластеры

Louvain на неориентированной проекции: вес пары равен сумме переводов в обоих направлениях; `seed=42`, `resolution=1`, `threshold=1e-7`. Направление теряется только для кластеризации. Узлы и рёбра добавлены канонически. Изоляты — отдельные кластеры. Номера от 1: по убыванию размера, затем по минимальному gid. Они не являются постоянными идентификаторами при изменении данных.

Внутренний оборот — сумма исходных направленных рёбер с обоими концами в кластере, каждое ребро один раз. `top_gids` — первые пять по приоритету. `stability` — средний лучший Jaccard с сообществами 20 прогонов с random seed 0–19; изоляты имеют 1. На данных 88 кластеров, из них 19 изолятов; у 60 из 69 кластеров с рёбрами stability≥0.8, минимум около 0.37. Это устойчивость к начальной случайности, не доказательство реальности групп.

Гипотеза использует модельный остаток seed участников: при ≥100 тыс. и концентрации ≥30% у одного узла — сбор; при меньшей концентрации и наличии веера с исходящими метками seed≥100 тыс. — рассылка, иначе рассредоточение. Если остаток мал, но ≥50% выхода участников требует неатрибутированного финансирования — окружение крупного плательщика. Далее проверяется наличие distributor; иначе признаки слабые. В тексте указаны роли, seed и stability. Все суммы остатков условны на модель.

## Сценарии блокировки

`resilience.csv` содержит `top` (весь рейтинг) и `top_new` (только не-seed), N=0,5,10,20,30. Для денежного сценария исключаются **исходящие** переводы заблокированных, остальные переводы сохраняются. Модель пересчитывается с нуля. Метрики связности отдельно описывают граф после удаления этих вершин целиком, а не граф с сохранёнными входами.

Все три категории остатков берутся из одного сценария **после** блокировки: остальные не-seed, заблокированные и незаблокированные seed. Знаменатель долей — маркированный объём исходного сценария. Потеря входа может вызвать дополнительное финансирование seed, поэтому новый объём не обязательно совпадает с базовым; `seed_kzt_origin_ratio` показывает изменение. Три доли суммируются в этот коэффициент, а не обязательно в 1. `seed_kzt_held_before_share` отдельно хранит исходный остаток будущих заблокированных.

На текущих данных, сценарий top_new (проценты от базовых 52 046 550.63 KZT):

| N | Крупнейшая компонента / число компонент | У остальных не-seed после | У заблокированных после | У тех же узлов до |
|---:|---|---:|---:|---:|
| 0 | 1877 / 35 | 91.44% | 0.00% | 0.00% |
| 5 | 1859 / 42 | 85.51% | 6.00% | 5.22% |
| 10 | 1846 / 50 | 80.58% | 10.93% | 9.39% |
| 20 | 1819 / 66 | 71.36% | 20.14% | 18.05% |
| 30 | 1800 / 73 | 63.14% | 28.36% | 24.50% |

Для N≥5 новый маркированный объём равен 100.0614% базового; ещё 8.5535% базового объёма находятся у незаблокированных seed. В top при N=30 у остальных не-seed 54.48%, у заблокированных 21.20%, у незаблокированных seed 5.29%, вместе 80.97% базового объёма. Это условный эксперимент с неизменными остальными переводами, а не прогноз поведения клиентов.

**Монотонность удержанного не гарантируется.** Если сначала заблокировать посредника, а затем сам источник, деньги перестанут поступать посреднику. Тесты проверяют конкретные балансы и соответствие сценарию, а не требуют искусственного роста показателя.

## Проверки и оценка

33 теста проверяют прежние правила и контракты, а также два seed в дневном цикле, цикл seed–клиент, исключение собственных возвратов, сохранение чужих меток, момент маркировки неизвестного входа, случайные графы с циклами, реальные остатки после блокировки, нулевой объём и удаление всего графа. Тест на предполагаемую монотонность заменён проверкой бухгалтерии и примером, где источник перестаёт финансировать заблокированного посредника.

Перед записью и после чтения проверяются схемы, уникальность и полнота gid, исходные атрибуты, степени/суммы/число транзакций, словарь и диапазоны ролей/скоров, evidence≤200 символов с числами, ограничения seed и границы, баланс меток по узлам и в сумме, размеры и обороты кластеров, ключевые gid и порядок топа. Отдельно проверяется баланс всех долей resilience. Результат при перемешивании строк исходных Parquet идентичен. Повторный запуск из другой директории с PYTHONHASHSEED=123 дал побайтово одинаковые шесть CSV.

Контрольный полный процесс 23.09.2026 — **3.28 с** (`real`), внутренний таймер **3.225 с** с импортами, записью и повторным чтением CSV. Лимит 300 с выполнен. Установка зависимостей не входит в замер.

Исправления устраняют воспроизведённые ошибки учёта, но не доказывают точность ролей. Сохранение состава топ-30 показывает устойчивость его состава именно к этим исправлениям; это не проверка всех порогов и моделей времени. Приоритет по-прежнему существенно зависит от допущений атрибуции, особенно от порядка операций внутри дня.

## Ограничения и масштабирование

Входы seed и входы извне графа неполны; начальные остатки неизвестны. Видны только внутрибанковские переводы от 5000 KZT за июль: нет межбанка, наличных, мелких переводов и августа. Пул модели не равен банковскому остатку. При расширении периода, каналов и временной точности атрибуция и роли могут измениться. Для проверки нужны полные выписки, время операций, остатки и исходящие за границей обхода. Роль coordinator — структурный кандидат, а не установленный организатор; кластер не является доказанной группой.

На примерно 1 млн узлов:

1. Читать Parquet пакетами через Arrow/DuckDB/Polars, агрегировать пары и дни вне памяти; деньги хранить целыми тиынами, gid перекодировать в плотные индексы.
2. Заменить плотные матрицы N×S источников и Python-графы на разреженные векторы меток и CSR/CSC. Дневные SCC и топологический обход считать нативным движком только для активных узлов. Не возвращать итерационную модель, допускающую самофинансирование циклов.
3. При многочисленных seed использовать bitmap/разреженные словари; top-k источников с остатком «прочие» допустим только с явной оценкой ошибки, поскольку точные seed_sources влияют на роли.
4. Louvain/Leiden и измерение устойчивости перенести в igraph/NetworKit. Учитывать изменение нормировки при разбиении расчёта на компоненты. Маршруты и циклы считать ограниченными соединениями и разреженными алгоритмами, не перечислять все пути.
5. Роли считать векторно, топ отбирать ограниченной очередью, CSV писать потоково. Сценарии блокировки требуют отдельных пересчётов; их можно распараллелить. Время и память измерить заново: текущие 3.28 с не экстраполируются линейно.

Текущая память: O(N×S+E+T), где S — число seed; дополнительный объём соответствует числу меток на переводах обрабатываемой компоненты. Перенос меток занимает примерно O(T×S), плюс построение дневных SCC/DAG и накладные расходы NetworkX; сортировки и группировки имеют отдельную стоимость. Бухгалтерские инварианты должны сохраняться при замене движка.
